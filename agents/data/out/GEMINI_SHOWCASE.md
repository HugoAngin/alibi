# How Alibi uses Gemini

Alibi runs Gemini as a team of agents, each with one role. The models propose, and code decides. Each row below links to evidence that is committed in this repo. Every number comes from a run you can repeat.

| What Gemini does | Model | Evidence |
| --- | --- | --- |
| **The Challenger chooses its own lookup.** The release message says the money reached Maya's *seller balance*. The Challenger refuses to treat that as a bank transfer, keeps the claim unresolved and asks for exactly one retrieval: `lookup_settlement {payout_reference: PO-5001}`. When the settlement record arrives, it is `pending` 2 hours after the credit was booked, so the Challenger moves the claim to **contradicted**. In the control run it is `settled`, so the claim becomes **supported**. In neither run did Argon propose `supported` before the settlement record was in front of it. | `gemini-4-argon` (thinking: medium) | [traces/contradiction.md](../../../alibi/REPORTS/traces/contradiction.md), [traces/supported.md](../../../alibi/REPORTS/traces/supported.md); summary in [S3.md](../../../alibi/REPORTS/S3.md) "Dev traces" |
| **Flash roles return structured output, and code checks every reference.** The Matcher, Detective and Curator answer in a JSON schema (`alibi/agents/prompts/*.json`). `validate_refs` ([models.py](../../../alibi/agents/models.py)) drops any `(record_id, revision)` that is not in the retrieved material. It also blanks a payout reference that no record carries and turns an action on an unknown ID into `none`. Status is decided by code from explicit fields: a model saying `supported` cannot raise a code verdict. Both live runs had 0 validation failures and 0 unsafe proposals. | `gemini-3.8-flash` (thinking: low) | [roles.py](../../../alibi/agents/roles.py) (`ROLE_MODEL`), [models.py](../../../alibi/agents/models.py) `validate_refs`, `alibi/tests/test_agents_runner.py` (26 tests) |

## The value of adaptive retrieval, measured so far

On the same pair of fixtures, a **one-pass Gemini baseline** (one call, fixed retrieval rule: "look up any payout reference named in a release message") performs **0 lookups**, because the release message names no reference. It therefore never sees the settlement record and leaves both variants **unresolved**. The agents perform **1 lookup** and reach the correct answer on both: **supported** and **contradicted** ([traces/one_pass.md](../../../alibi/REPORTS/traces/one_pass.md)).

| On the demo pair (dev fixtures) | Lookups | Bank A answer, supported variant | Bank A answer, contradiction variant | Model calls (RFC A) | Tokens (RFC A) |
| --- | --- | --- | --- | --- | --- |
| One-pass Gemini | 0 | unresolved | unresolved | 1 | ~6,600 |
| Alibi agents | 1 | **supported** | **contradicted** | 4 | 25,498 / 27,800 |

These are 2 development fixtures, not a benchmark. **Measured on sealed cases: pending.** Eval scores Alibi against the rules baseline and one-pass Gemini on the sealed cases; when its verified rows land in `agents/eval/out/results.jsonl`, this section quotes them with denominators and intervals. On the 80 development cases, the reference often appears in the release message itself, so we expect a smaller gap there than on this pair.

## Limits we state plainly

- The traces above use the S3 development fixtures (`txn_9001`, `PO-5001`). The app on `main` (`2842b58`) runs **rules-only**: the agent roles are not wired into it yet. S5 wires them and records replays for case 1 (QA_0430.md #6).
- Gemini proposes; code computes every total and decides every status. A valid package signature proves who sent it and that nothing was altered. It does not prove any claim is true.
- Whether a real bank would accept this is unmeasured.
