## What works

- **Case 1 travels end to end through real endpoints.** `test_connectors_plug.py` wires a passport
  store to a merchant app (webhook sink) and a bank app (RFC sink) in process: `bootstrap` seeds the
  merchant (20 signed pushes, all `inserted`), syncs the feed (4 rows, cursor `c:4`), has both banks
  issue their RFCs (`receive_rfc` accepts both), then `run_investigation(mode="rules")` runs with the
  real connector callables, `build_review` / `approve` / `sign_and_package` produce packages, and
  `POST /deliver` verifies them in the right inbox only. A `request_more` disposition creates a
  follow-up RFC that the passport accepts with `parent_request_id` and the parent's `txn_ids`; the
  follow-up gets its own investigation, approval and package. `test_demo_services.py` repeats the
  seed, feed sync, RFC intake and lookup over real sockets with `httpx` against uvicorn on ephemeral
  ports.
- **Mapping without interpretation** (`MAPPING.md`): every event, import, bank row and RFC in all 70
  development cases maps to a validated core object; references in free text stay text.
- **Merchant**: pushes in the data layer's arrival order, duplicates, conflicts and stale revisions
  included, each signed with `merchant_mock`; the passport's verdict is reported per delivery and
  agrees with `gold.ingest` on cases 1, 2, 21, 23, 27, 28, 30 (see "Core gaps" for the one label
  difference). Lookups serve exactly what `agents.data.api.lookup` defines at the clock.
- **Bank**: two identities with separate tokens, inboxes, requests, dispositions and audit; the
  recipient and analyst come only from the token. Delivery verification passes the issued RFC's
  `subject_ref` and `request_id` into `verify_package` and reports authentication, per-source trust
  and claim status separately. Rejections store reasons and digests only.
- **Feed**: cursor and batch commit together through `ingest_bank_txns`; any failure leaves the
  cursor where it was; provenance carries connection, retrieval time, feed version and cursor.
- **Retrieval through the gateway is real.** On case 3 (a pushed, settled payout)
  `run_investigation` calls `lookup_settlement("PO-0003-01")`, which reaches the merchant's
  `/settlements` route and is logged in its `/admin/lookups`
  (`test_connectors_plug.py::test_investigation_reaches_the_merchant_on_a_case_with_a_pushed_payout`).
  On case 1 the rules engine never gets that far, because nothing pushed is a payout (core gap 2).

## How it was built

Lead wrote the keystone (`case_source.py`, keys, the shared refusal helper, the sinks), the
mapping document and the route contract (`SERVICES.md`) first, so three builders could work on
disjoint files in parallel: the merchant, the feed and import, the bank service. Each module then
had a correctness reviewer and an adversarial reviewer, and a fixer applied the confirmed findings
with regression tests (24 fix entries in that round, for example: empty lookup keys crashing the
merchant with a 500, push order diverging from `gold.ingest` order in five cases, a feed client that
could loop forever on a non-advancing cursor, unvalidated package fields echoed into bank reasons
and audit, a custom RFC that could squat the other bank's request id in the passport). Lead then
wrote the clients, `bootstrap`, the demo runner and the integration tests. A final review pass
(adversarial, correctness, completeness against the brief) found 14 more real defects, all fixed
with regression tests: `bootstrap` returned a normal summary when the merchant's pushes had failed,
hostile merchant values could reach the persisted trace unbounded, malformed service answers
crashed the clients instead of raising `ClientError`, a `TypeError` from a hostile RFC body was a
500, a numeric time in a merchant correction poisoned the lookup pool, and the demo runner printed
its ready line before binding and could hang behind a port clash (it now reports within 15 s and
exits 1). Two findings were documentation only and are reflected in `SERVICES.md`.

## Decisions worth knowing

- **Signing key.** The brief said to sign with `merchant_demo`, but the core pins that key to the S1
  issuer `threadline`, and `ingest_merchant_event` refuses a key pinned to another issuer. The
  connectors sign with a fifth demo key, `merchant_mock`, pinned to `mock-marketplace`
  (`connectors/keys.py`). `connector_keystore()` writes a five-key registry; pass it and its
  registry explicitly to every passport call, because `alibi.api.default_keystore()` rewrites the
  file with four keys (`NEEDS.md` item 1).
- **One core kind per case payout.** The store's record identity includes `kind`, so a case payout
  (status plus `settled_at`) is one core `payout` with `status` and `effective_at`; there is no
  derived settlement record and no record id is invented. `GET /settlements?payout_reference=`
  returns that payout.
- **No text parsing in the connector.** A withdrawal reference quoted in a balance-release message
  stays in `text`. Parsing it would hand every system the hidden-reference answers.
- **`extra` never enters a signed payload.** The core models reject unknown fields, so the case
  fields the core cannot hold travel beside `{event, signature}` and are stripped by the plug.
- **Visibility follows the data layer.** `available_from` and `received_at` decide what the services
  serve; the clock is floored to whole seconds and only moves forward.
- **Follow-up ids** are `<parent>-f<n>` unless the analyst supplies an unused id; neither bank can
  use a case RFC id or an id the other bank issued.

## Core gaps (documented in `alibi/NEEDS.md`, not fixed here)

1. `merchant_mock` should join the core's `DEMO_KEYS`.
2. The rules engine and gateway accept only `kind: settlement` as settlement evidence, and the
   gateway only looks up a reference carried in an issuer record's `payment_ref` field. On the
   team's cases the lookup-only payout is therefore never retrieved by `run_investigation`, and case
   1's source-of-funds claims stay `unresolved`. `test_connectors_plug.py::test_gateway_ingests_the_case_payout_as_settlement_evidence`
   is a strict xfail that turns into a failure the day the core accepts it. The plug's
   `settlement_lookup` already returns the right signed record (`::test_settlement_lookup_returns_the_signed_payout_only`).
3. `q.sales_refunds_in_period` ("sales and refunds") is classed as "several totals" and stays
   `unresolved`, so bank_b's package carries no evidence.
4. `BankTxn` has no counterparty field and merchant records no withdrawal-id slot; both stay in
   `extra`.
5. A redelivered superseded revision is labelled `duplicate` by the store where data's gold says
   `stale_revision_ignored` (case 23); the passport state is right, only the word differs.
6. The new refusal codes need pinning in `shared/CONTRACTS.md`.

## What failed or changed course

- Two shell heredocs failed to parse under Git Bash on long Python sources; files were written with
  the editor tool instead. No retry loops were needed anywhere; there is no `BLOCKERS.md`.
- The bank builder had to wait for nothing: the feed module landed in parallel with the exact
  interface in `SERVICES.md`, and the integration tests confirmed the join.
- Reviewers' cross-module recommendations (a shared handler for unknown paths and methods,
  `ValueError`/`TypeError` as a 400) were folded into `connectors/http.py`.
- Two wording differences from the brief: the case 2 payout is visible from its `available_from`
  (06:35Z), five minutes after its `status_as_of`, because that is the data layer's rule; and on
  case 1 the rules investigation never calls the merchant (core gap 2), so requirement 5's
  retrieval is proven on case 3 instead.
