# Alibi contracts, v1

Owned by `lead`. The full contract text is the "Technical contracts", "Agent boundaries" and "Consent and signing" sections of `alibi/SPEC.md`. This page pins the decisions agents build against in parallel. To change one, post a `need` to `lead`. Actual routes, commands and JSON schemas are published by their owners once wired, and `lead` links them here.

## Pinned decisions

| Topic | Decision |
| --- | --- |
| Money | Integer minor units plus ISO 4217 code. The demo currency is `GBP`, so amounts are pence. Code never converts currencies. |
| Time | UTC, ISO 8601 with `Z`. Periods are half-open `[from, to)`. |
| Canonical fixture | Sales `240000`, refunds `18000`, fees `6000`, bank credit `216000`. One fixture in the app, tests, slides and recorded demo. The fixture is data's case 1, `agents.data.api.canonical_case()`, with case 2 as its contradicted twin: subject `maya-001`, issuer `mock-marketplace` ("Mock Marketplace Payments" on the bank row), credit `txn-0001-004` booked 2026-10-28 with reference `PO-0001-01`, balance release `rec-0001-020` (`REL-0001-01`) pushed on 2026-10-26, payout `rec-0001-021` settled 2026-10-27 and reachable only by lookup, RFCs `rfc-0001-01` (bank_a, that txn) and `rfc-0001-02` (bank_b, October 2026 period). The mock merchant and bank services, UI samples and demo script load these IDs from the case rather than inventing their own. The builders are `agents.eval.api.build_mock_merchant`, `build_mock_bank` and `build_analyst_preview`, each taking `canonical_case()`; build sessions import them instead of hand-writing samples. |
| Recipients | `bank_a` and `bank_b`. One mock bank service, two credentials, two inboxes. Isolation is enforced by authenticated recipient scope, never by a UI selector. |
| Trust | Source trust is one of `issuer_verified`, `bank_observed`, `self_supplied`. Imports are tagged `self_supplied` by the backend whatever the user says. Trust describes the underlying record's issuer, so it stays at three values. Each `source_trust` and evidence item also carries `attestation`, one of `issuer_signature`, `package_signer` or `none`, and `redacted: bool`, the same fields the export view already uses. A redacted extract keeps the trust of the records it summarises, has `attestation: package_signer` and `redacted: true`, and the UI shows it as "Redacted extract, attested by Alibi" beside the issuer badge. Never badge an extract as if the issuer signed it. |
| Link state | One of `unmatched`, `ambiguous`, `linked`. Exact matching needs one unique compatible candidate. |
| Claim status | One of `supported`, `contradicted`, `unresolved`. `contradicted` means evidence conflicts with the claim; `unresolved` means the evidence is unavailable. Link state, trust and claim status are three separate fields. |
| Settlement timing | A payout released to a platform balance is not a bank settlement. A later payout never explains an earlier credit because the amounts match. |
| Identity | Merchant events: `schema_version`, `event_id`, `record_id`, `revision`, `issuer_id`, `subject_ref`, `kind`, `occurred_at`. Bank rows: stable `txn_id`, `revision`, signed amount from the holder's view. RFCs: `request_id`, `subject_ref`, `audience`, period or `txn_ids`, question IDs, expiry; follow-ups get a new `request_id` and a parent reference. |
| RFC scope | An RFC is scoped by exactly one of `period` (half-open, else `null`) or `txn_ids` (non-empty, else `[]`). The canonical `rfc-0001-01` is transaction-scoped with `period: null`; `rfc-0001-02` is period-scoped with `txn_ids: []`. Every consumer, including the analyst package view and the signed package scope, handles both: show the period when set, otherwise the transaction IDs, and never dereference `period.from` without a null check. A transaction-scoped package signs over the actual `txn_ids`, not a derived booking-day window. A follow-up RFC created by `request_more` keeps the parent's scope kind and values by default (`rfc-0001-03` from `rfc-0001-01` is transaction-scoped with the same `txn_ids`), and the follow-up form must offer the same two scope choices as RFC intake, never a period-only field. Widening the scope beyond the parent is a new RFC, not a follow-up. Every `txn_ids` entry must be a transaction in the authenticated recipient's own bank feed for that subject; otherwise the RFC is refused with 4xx `txn_out_of_feed` (SP-23). |
| Idempotency | By connector and `event_id`. Same ID with different bytes is rejected. Corrections append a newer revision and keep the old one. A stale revision cannot replace the active one. |
| Signing | Ed25519 over JCS canonical JSON (`rfc8785`), separate record and package signing domains, envelope with algorithm, key ID and signature. Separate mock-merchant and Alibi demo keys. The app key comes from `ALIBI_MASTER_KEY` in `.env`. The app's verifier is `agents.lead.api.verify_package`; bank-side callers must pass `expected_subject` and `expected_request_id` (S1 open issue 4). Independent check, no `alibi` import: `uv run --frozen python -m agents.eval.verify_package PACKAGE --registry PINNED_KEYS --recipient bank_a [--at UTC_TIME]`; every delivered package must pass it. |
| At rest | The at-rest claim (SP-47) covers the passport store only: evidence payloads are ciphertext and `ALIBI_MASTER_KEY` is held outside the data folder. The app's demo state file (`case_N.state.json`) and the mock bank's `state.json` hold delivered packages in plaintext (eval cd71c90; confirmed on frozen S5 c6ea270 for the standalone bank, 20 and 10 attachments, evidence `agents/eval/out/s5-bank-persistence-sp47.json`, 2ce3bb2), and the README and deck say so unless S5 encrypts them before freeze. A delivered package is the recipient's copy, in the recipient's custody. |
| Approval | Holder decision bound to SHA-256 of the canonical body, audience, `request_id`, policy version and source revisions, with a short validity window. Any change invalidates it. Each recipient and request needs a fresh approval. Reference implementation of the full consent matrix: `agents.execution.approval_gate` (`ApprovalGate`, `CONSENT_MATRIX`, `body_digest`), with `register_request`, `set_draft`, `approve`, `dispatch`, `policy_changed`, `source_corrected`, a 15-minute window, single use, and every refusal `{ok: False, status: 409, code, reason}` with the matrix's verbatim reason and an audit entry. The app's dispatch path calls it or must pass the same C1 to C16 tests. |
| Agents | Matcher, Detective, Challenger, Curator. Deterministic joins run first. Each role has separate inputs and a schema-validated output. The backend owns arithmetic, policy, consent, signing and delivery. |
| LLM | Gemini through `google-genai`, key name `GEMINI_API_KEY`. Model IDs as set in `alibi/llm/config.py` on the s3a build: `gemini-3.8-flash` (thinking low) for routine calls and `gemini-4-argon` (thinking medium) for the frontier role, both confirmed live on 2026-11-07. The one-pass Gemini baseline uses the same model as the Alibi role it stands in for and reports any difference. Every model call appends one row to `data/alibi/llm_log.jsonl` (format in `alibi/llm/client.py`) carrying `case_number`, `system` (`rules`, `gemini_onepass`, `alibi`) and a run ID, with usage from the API response; each scored run starts a fresh log per system. `uv run --frozen python -m agents.eval.llm_cost --log <file>` turns it into `model_calls`, `tokens` and `cost_usd_estimate`, and rows without usage or scope count as unknown, never zero. |
| Policy | A holder's privacy rule is compiled once into typed rules, kind one of `deny`, `generalise`, `age`, `recipient`, each with target fields, or left `unresolved` and held for clarification; the parser never guesses. Enforcement is deterministic: deny wins over every other rule, a withheld item leaves a generic gap and never a hint of what was withheld, and the filter runs after the agents and before approval, so the holder approves exactly what the filter produced. The fixture of 40 plain-English rules with expected compilations is `agents.execution.api.load_policy_rules()`; the reference compiler and filter are `agents.execution.api` (`compile_policy`, `apply_policy`), and the app's parser is `agents.lead.api.parse_rule_text` with typed rules `DenyRule`, `GeneraliseRule`, `AgeRule`, `RecipientRule`; execution's harness scores the app's parser on the fixture and the two must agree on it. |
| Disposition | Analyst decision on a delivered package, recorded bank side: `disposition_id`, `package_id`, `package_digest` (SHA-256 of the package), `request_id`, `recipient`, `analyst`, `decision` one of `clear`, `escalate`, `request_more`, `reason`, `question_ids`, `requested_evidence`, `decided_at`, `supersedes`. Visible to the deciding recipient only, never sent to the holder automatically and never an input to an automated account decision. `clear` and `escalate` are terminal for that package. `request_more` creates a follow-up RFC with a new `request_id` and `parent_request_id`, which needs fresh holder approval. There is no separate follow-up route: the console posts `request_more` with `requested_evidence` to `POST /packages/{id}/disposition` on the bank service, which issues the signed follow-up (`<parent>-f1`) with the parent's scope; a second decision on a terminal package is `409 disposition_final`. Full checklist: `agents/execution/out/ANALYST_FLOW.md`. |
| Refusals | Any backend action that refuses (approval invalidated, scope mismatch, stale revision, policy violation, bad credential) answers with a 4xx status and a body `{"code": <stable snake_case code>, "reason": <the backend's own sentence>}`, the same code and sentence the HTML path shows and the audit log records. Codes are the ones in `agents/execution/out/consent_matrix.md`; a new code is a `need` to `lead`. Front ends display `reason` verbatim and never invent their own. A request whose declared issuer, recipient or subject differs from the authenticated credential is refused with `issuer_mismatch` (or `recipient_mismatch`, `subject_mismatch`), never silently rewritten to the authenticated identity (SP-22, SP-24). |
| Case schema | A case is the JSON object described in `agents/data/README.md` (Case layout): `merchant_deliveries`, `merchant_lookup`, `imports`, `bank_deliveries`, `rfcs`, `holder_claim`, and for labelled cases `gold`. Development cases are one file per case in `agents/data/out/cases/`, gold embedded, loaded with `agents.data.api`. Sealed and adversarial cases use the same schema, one JSONL record per case without `gold`, with gold in a separate evaluator-only file keyed by case number and `request_id`. Sealed gold keeps `requires_retrieval`, so the report can split cases that depend on a lookup from those that do not. Neither sealed file is committed until the candidate is frozen. Systems under test receive only what `known_at(case, decision_time)` returns and reach lookup-only records through the lookup interface. Receipt images for the vision import are `agents/data/out/receipts/*.png`, every one stamped SYNTHETIC, with the true fields and the `case_number` and `record_id` each links to in `agents/data/out/receipts/receipts.json`; the set includes case 1's forbidden eyewear purchase (never disclosed) and a handwritten private sale with no record (stays unlinked). Whatever the vision model reads, an imported receipt is `self_supplied` and never part of an evidence set. Rebuild: `uv run --frozen python -m agents.data.receipts`. Cases 71 to 80 come from a second platform, issuer `second-platform`, whose raw events use its own schema `sp-2.1` (`order_completed`, `order_returned`, `service_charge`, `weekly_statement` with `net_payable_pence`, `transfer_status`, `paid_at`, `line_record_ids`; bank reference format `SPLAT Wnn nnnn`) and never carry contract field names. `agents.data.api.to_contract(event)` is the reference mapping to the contract kinds; gold applies the pinned rules after it, and cases 79 and 80 have Maya on both platforms in one month, so Bank B's period answer carries `facts.by_issuer`. A connector for a new issuer is a mapping to the contract, never a change to the contract. |
| Questions and matching | Question IDs are `q.source_of_funds`, `q.breakdown` and `q.sales_refunds_in_period`. A settlement candidate is one settled payout or one whole `settlement_batch_id` group whose total equals the credit, with `settled_at` at most 5 days before `booked_at` and never after it, and whose `payout_reference`, `settlement_batch_id` or `withdrawal_id` equals the bank `payment_reference` when one is present. The lookup interface takes exactly one key: an exact `payout_reference`, a `record_id`, a `covers_record_id` or a `payout_date` (`YYYY-MM-DD`); there is no fuzzy lookup. Merchant `notice` and `statement` events carry free text and no amounts, and may be the only place a reference appears. Gap codes are the nine listed under Gold rules in `agents/data/README.md`. Hidden-reference gold (cases 41 to 50) adds `retrieval_path` and `clue_refs`, which the report uses to split retrieval failures from reasoning failures. Injection cases (51 to 60) are exact copies of case 1 or 2 with one string from `agents.execution.api.load_injections()` planted; their gold equals the base case's plus `gold.injection` with the carrier path, string, expected behaviour, `forbidden_strings` and probe IDs, so a scorer checks the base answers and the injection outcome separately. Alert cases (61 to 70) raise proactive alerts before the first RFC; `gold.alerts` uses the `alibi/app/UI.md` alert shape (`kind`, `severity`, `raised_at`, `subject_ref`, `facts` with source refs, `suggested_checks`) with kinds `unexplained_credit`, `unusual_inflow`, `unusual_outflow`, `amount_discrepancy`, `settled_not_received`, `settlement_discrepancy`, `merchant_unverified`, and the rules in `agents/data/README.md` are the gold for the monitor. The same monitor gives demo cases 1 and 2 an `unexplained_credit` on 2026-10-29, before the RFC, which is the alert the demo opens on. Merchant identity comes from `agents.data.api.merchant_lookup(query, checked_at)` over `agents/data/out/merchant_registry.json`, returning UI.md's `merchant_lookup.result` shape; `unknown` means unverified, never fraudulent. These are the gold rules for the rules baseline and the scorer; the Alibi agents may use anything observable but are scored against them. |
| Prediction | Published: `alibi/eval/predictions.md` with schema `alibi/eval/schemas/prediction.schema.json`. One object per (case number, request) with `claims` by question ID, `package`, optional `proposed_package` (pre-policy, scored as `unsafe_proposals`), `exclusions`, `cost`, `retrieval` and `failure`; refs in gold's `bank:`, `merchant:`, `import:` form. Scorer: `uv run --frozen python -m alibi.eval.scorer --predictions <files> --names <names> --by-family`; gold-derived example `python -m alibi.eval.oracle`; rules system `python -m alibi.eval.rules_reference`. The interim shape lead pinned earlier is withdrawn; this file wins. |
| App adapter | Published: `from agents.lead.api import ...` (same `__all__` as `alibi.api`), documented with JSON examples in `alibi/CONTRACTS.md`. Ingest a case with `ingest_merchant_event`, `ingest_bank_txns`, `import_self_supplied` and `receive_rfc`; `run_investigation(store, request_id, mode="rules", now=...)` returns an `InvestigationResult`; `build_review`, `record_policy`, `approve`, `sign_and_package` and `verify_package` cover review to delivery. `parse_rule_text` is the plain-English rule parser. Modes other than `rules` raise `NotImplementedError` until S3 lands. Known open issues are listed in `alibi/REPORTS/S1.md`; the S1 report also says its schemas were not aligned with this file, so until lead confirms otherwise the question IDs, gap codes and 5-day rule here are the scoring truth and `alibi/core/schemas.py` is being compared against them. |

## Results format

`tools/results.py add` records a command that prints one JSON object on its last line. For this task the headline metrics are case rates, not returns:

```json
{"cases": 32, "safe_complete": 27, "safe_complete_rate": 0.844,
 "match_precision": 0.97, "match_recall": 0.95, "unmatched": 3,
 "citation_accuracy": 0.96, "gap_recall": 0.9,
 "forbidden_items": 0, "unnecessary_items": 1,
 "probes_blocked": 11, "probes_attempted": 12,
 "unsafe_proposals": 4, "lookups": 36, "observed_inputs": 410,
 "model_calls": 140, "tokens": 182000, "cost_usd_estimate": 0.41}
```

Report every system (rules baseline, one-pass Gemini, full Alibi) with the same keys so the README table lines up. `unsafe_proposals` counts packages the policy gate rejected before delivery, so pre-policy behaviour is compared and not hidden by the common gate. `lookups` and `observed_inputs` count lookup calls and records read across all cases, which the SPEC asks the baselines to report against their predeclared fixed retrieval strategy. Failures and abstentions count in the denominators. Keep the exact-answer scorer separate from any human review of explanations.

## Split and lockbox

`shared/splits.json` sets `lockbox_from` to a case number. Development and demo cases are numbered below it. The sealed evaluation and adversarial cases are numbered from it upward, are authored by `eval` from separate scenario families, and are not committed until the candidate is frozen. `eval` scores them once with `results.py add --split lockbox`. The demo fixture and its variants are never in the sealed set.

Sealed runs are local only. `eval` runs them on its own machine, from a clean checkout of the frozen commit, in-process through `alibi.adapter.run_case` inside `agents.eval.sealed_worker`. No sealed case, gold or package goes to any shared or public deployment (Modal, Cloudflare, a tunnel), the board, or a commit before freeze. The only outbound calls are the Gemini API calls the system under test makes itself, with the run's own key. The only things that leave the machine are the scores and the `results.py` record. Shared deployments run public cases 1 to 80 only.

It is the facts fix 9468c20 plus the trace clip under the 10:48 condition, and it supersedes `sealed-candidate-2` (9468c20) before the pack opened. Record `--variants 3`. They apply to `sealed-candidate-2` if it is tagged by 11:15 London (lead post 6720509694: typed `Claim.facts` in both Gemini modes, computed by code, statuses and evidence unchanged), and otherwise to `sealed-candidate` (c6ea270). Nothing changes after the tag:

1. **Isolation.** Each worker runs from its own disposable copy of the tagged tree (a fresh `git worktree` or archive extract), with `ALIBI_DATA_DIR` in private scratch. The copy is deleted after its scores are written. The team checkout is never written to, so live recordings of sealed cases cannot reach the repo or a later worker. Replay reads only tracked recordings. A tracked file changed by a public rehearsal is restored with `git checkout -- <file>`.
2. **Policy field.** The canonical case field is `holder_policy`, which is what the frozen adapter reads. The evaluator's case loader maps `privacy_policy` to `holder_policy` before the worker sees the case. Before the pack opens, one public synthetic restriction must be shown to take effect through the worker.
3. **Cost.** Each worker copies its `llm_log.jsonl` to private scratch before cleanup, and `agents.eval.llm_cost` computes cost from the logged usage. Where usage was not logged, cost is reported as unknown, never as a measured 0.0.
4. **Baselines as configured.** The comparison is agents against the rules baseline and the one-pass baseline as frozen. The one-pass baseline retrieves only references named in balance-release messages, and rules uses its broader reference pool. The README and deck say so, and claim nothing about equal retrieval.
5. **Time budget.** Per-case limits: agents 120 s, one-pass 60 s, rules 30 s as first pinned; the bound capture config actually used 180 s, 90 s and 30 s (eval, second-candidate binding 80a4e17), and that config is authoritative for the first attempt and the resume. Workers may run in parallel up to the Gemini rate limit. A timeout counts as a failed case and is never dropped. Hard stop at 11:50 London: each system reports the cases completed out of the cases attempted, with the stop reason. The lockbox record is made once with `results.py add --split lockbox`, and execution reruns `results.py verify`.

6. **What the score measures.** The scorer reads the adapter's top-level `claims`, which the investigation produces before the holder's policy is applied. The headline score is therefore reported as investigation (draft-evidence) correctness. `package_claims`, the policy-filtered claims the recipient actually receives, are reported separately: the number of RFCs where they diverge from `claims`, and why. No README, deck or results line may say the score proves the correctness of the claims a recipient receives after policy. Post-policy disclosure is evidenced by the leak and restriction checks instead, for example 30 of 30 `amount_pence` fields removed in the public restriction test.
